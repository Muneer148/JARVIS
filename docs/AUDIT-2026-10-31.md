# JARVIS repository audit — 31 October 2026

## Executive verdict

**Partially aligned foundation; not yet aligned implementation.**

The repository has a useful single-agent Python foundation and several sensible safety-oriented design decisions. It does not yet implement the multi-agent orchestration, worker isolation, persistent operational telemetry, or SOC-inspired Agent Operations Console required by the agreed JARVIS direction.

The existing code should be evolved rather than discarded. The architecture documents added alongside this audit describe the target and explicitly distinguish planned components from existing code.

## 2. What is already implemented on dev/jarvis-v1

### Agent and tool foundation
- main.py starts a synchronous command-line loop.
- brain/planner.py contains one Agent instance with an in-memory message history.
- The model can request one registered tool per tool round using a textual TOOL_CALL format with optional JSON arguments.
- MAX_TOOL_ROUNDS bounds tool rounds for a single request.
- tools/base.py defines ToolSpec with permission, risk, reversibility, approval metadata, and a generated schema description.
- tools/registry.py registers filesystem, diagnostics, memory, browser, and terminal tools.

### Model routing
- Provider adapters exist for Ollama, OmniRoute, NVIDIA, and OpenRouter.
- brain/router.py uses a heuristic to keep short routine requests local and escalate selected complex/long requests to configured hosted routes.
- Handled cloud failures fall back to Ollama.
- Model routing and tool routing are already conceptually separate.

### Tools and safety foundation
- Downloads analysis is read-only.
- Downloads organization has a deterministic plan, validation, approval metadata, post-move checks, and best-effort rollback.
- The terminal tool is disabled by default.
- The browser tool is a static public-page fetcher with URL and redirect checks; it is not a full authenticated or JavaScript-capable browser automation system.
- Diagnostics can inspect machine resources and project health.
- An explicit local memory tool exists.

### Testing and CI
- Tests exist for browser fetching, environment loading, filesystem behavior, memory, permissions, planner, router, and safety validation.
- A GitHub Actions test workflow exists and configures Python 3.12.
- This audit inspected test files and workflow configuration but did not execute the test suite. No claim that the current suite passes is made here.

## 4. Important code-level findings

### A. One agent, not an agent swarm
brain/planner.py defines one Agent and one sequential tool loop. There are no agent identities, task contracts, task ownership, delegation, cross-agent handoffs, work queues, or durable run records.

### B. No event/audit pipeline
The current CLI prints activity to the console and keeps conversation messages in process memory. There is no persistent event table, run ID, trace ID, task ID, span hierarchy, or dashboard query layer. This is the first major capability to add before a visual operations console.

### C. FreeLLMAPI is not wired into the source
The repo currently uses OmniRoute and direct NVIDIA/OpenRouter adapters as optional routes. The selected local FreeLLMAPI gateway is installed and has been smoke-tested separately, but there is no code adapter or runtime compatibility matrix in the current implementation.

### D. Hosted routing has no data-classification gate
The current heuristic can route a longer or explicitly complex conversation to a hosted provider. The router does not classify the sensitivity of the conversation or require approval before sending its contents to an external provider. Add privacy classification and external-provider policy before using the router with private documents, credentials, or sensitive project data.

### E. Tool-call contract is text-based
The planner parses a textual TOOL_CALL line with a regular expression. ToolSpec exposes a schema description, but the current call path does not implement a full native tool-call protocol or complete JSON Schema validation at the execution boundary. The next iteration should validate required keys, types, unknown keys, path scope, and permission arguments before tool execution.

### F. Approval state is not durable
The current PermissionEngine can ask a console callback to approve a privileged tool. It does not persist an approval record or support a dashboard queue, expiry, action-bound approval IDs, or remote pause/resume. This is a foundation, not the final approval workflow.

### G. Terminal execution is not ready to enable
tools/terminal.py uses subprocess execution with shell=True and a small dangerous-substring blocklist. This is not a robust security boundary. The feature is disabled by default; keep it disabled until the stricter execution model in SECURITY.md is implemented and tested.

### H. Browser network boundary needs further hardening
The static fetcher checks DNS results and revalidates redirects, which is a good starting point. However, hostname resolution and the later network connection are separate operations; DNS rebinding/TOCTOU risks need a stronger network boundary and adversarial tests. Do not interpret the present checks as a complete network sandbox.

### I. Memory implementation needs one clear source of truth
The active tool registry imports tools/memory.py, which implements a local JSON-backed store with keyword scoring. A separate memory/database.py and memory/memory.py provide a small SQLite-based implementation but are not used by the active registry. Decide whether to keep, consolidate, or remove the unused path before expanding memory features.

### J. Python version documentation was inconsistent
The old development README said Python 3.14+, while the checked-in GitHub Actions workflow configures Python 3.12. This documentation branch now states Python 3.12 or later as the current CI baseline; verify the supported runtime in CI and local environments before raising the minimum version.

### K. No workspace isolation
Workers do not currently have dedicated branches/worktrees or filesystem boundaries. This must be implemented before multiple coding agents are allowed to operate on the repository.

### L. Voice feature branch is separate
feature/voice-assistant diverges from dev/jarvis-v1. Treat voice as an optional capability after core agent, policy, and telemetry work; do not bring it into the target architecture by merging without review.

## 5. Existing strengths to preserve

- A central ToolSpec abstraction.
- A separate PermissionEngine instead of embedding all safety checks in prompts.
- Deterministic Python handlers for filesystem actions.
- A local-first default and provider adapters.
- Explicit memory tools rather than arbitrary implicit memory writes.
- Test coverage for several core modules.
- A CI workflow that runs tests on pushes and pull requests.

These are useful building blocks. Keep them where they fit, but strengthen their contracts before increasing autonomy.

## 6. Required changes, in order

1. Add a central structured event interface and persistent run/task/event state.
2. Add privacy classification before any hosted model call.
3. Enforce argument, path, role, and tool-level policy at the execution boundary.
4. Harden terminal execution; leave it disabled until the security gate passes.
5. Add the FreeLLMAPI adapter and model/runtime compatibility tests.
6. Connect Hermes and OpenClaw behind explicit interfaces and bounded run state.
7. Add per-task Git worktrees and one write owner.
8. Add coding/research worker adapters and an independent QA Sentinel.
9. Build the operations dashboard from actual persisted telemetry.
10. Add optional bounded swarm behavior only after sequential workflows are reliable.

## 7. Audit limitations

This was a GitHub source and branch inspection. The code was not cloned or executed in this audit session, the tests were not run, and no dynamic security assessment was performed. Code-level observations are based on the inspected files. Runtime behavior, provider availability, and account quotas must be revalidated in the user's local environment.

## 8. Outcome

The repository is a valid starting point for the JARVIS target, but it should not be described as a multi-agent Jarvis or SOC console yet. The architecture, operating model, security, observability, model routing, and roadmap documents define the intended direction. The next coding milestone is the telemetry spine for the existing single-agent path, not adding a swarm.
